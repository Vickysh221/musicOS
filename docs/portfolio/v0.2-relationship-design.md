# v0.2 · 把"关联"做成界面

v0.1 解决的是"播放"，没解决"为什么"。一份歌单把顺序告诉用户，把关系藏起来；作为节目形式，播客的结构因此被丢掉。v0.2 这一版只解决一件事：让歌曲之间的关联在听的过程中自己显形，不要求用户先去解读它。

## 把关联拆成两个互为镜像的面

我把"关联"建模成同一件事的两个面：

- **歌 → 歌**：当下播放的曲目和它相关的几首，视觉上同时在场。
- **口播 → 歌**：转写稿里被提到的歌名，是可点的胶囊。

两面背后是同一根数据线：句子里识别出来的歌名，映射到节目里对应的曲目位置。这条数据线决定了 UI 上它们必须绑定：弧亮起来的同一时刻，胶囊也亮起来；点哪一边都收敛到 goToTrack 这一个动作。这是 v0.2 最核心的承诺，后面所有动效和状态都围着这一点设计。

## 探索过程

走到这个形态之前砍掉了三条岔路（见下方 diagram）：星系、信息图谱、黑胶透出。三个都失败在同一个地方：它们让"关系"成了一个需要被解读的图层，而不是叙述本身的延伸。

留下来的是焦点圆盘 + 命中弧 + 封面环；具体三态可以在 diagram 里走查。

## 两条交互承诺

设计落地时反复回到两条原则：

1. **关系跟着叙述长出来。** 用户的认知姿势是"听"，不是"读图"。结构必须在他听的过程中自己显形，而不是要求他先理解一张图再开始听。
2. **两面任意一处都接得住。** 听不看屏幕时，可以稍后回看图像那一面；想读句子时，可以从词跳到歌。中间没有模式切换，只有同一份数据的两种密度。

PC 端把这套机制延伸成"听 / 瞄 / 看"三种密度（diagram 里有完整三态），移动端是它们的精装压缩版。

## 留下的约束

可被点击的封面环最多四到五枚，再多就开始拥挤。这意味着每集节目能引入的"亲缘"必须被脚本预先收敛到这个数量级。这不是 UI 限制，更像是一种创作约束：节目本身要写得更克制。
